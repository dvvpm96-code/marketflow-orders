# Установка через GitHub Actions — без входа через ChatGPT

GitHub собирает и проверяет приложение, затем по SSH устанавливает его на ваш Ubuntu-сервер. Сам кабинет работает на сервере: Node.js, SQLite, HTTPS и собственные логин/пароль. Ни ChatGPT, ни учётная запись GitHub для посетителя кабинета не нужны.

GitHub Pages предназначен для статических страниц и не запускает эту серверную часть. Старый адрес Sites продолжает работать отдельно; он автоматически не переключается и не переносит данные.

## 1. Подготовьте домен и сервер

- Ubuntu 26.04 с systemd, amd64 или arm64, доступ по SSH от `root`.
- Ваш домен, например `orders.example.ru`, с DNS A на адрес сервера. Если есть AAAA, она тоже должна указывать на этот сервер.
- Сервер доступен GitHub-hosted runner по SSH. Порты 80/443 доступны для HTTPS и выдачи сертификата.
- Первая установка: нет `/opt/marketflow`, `/var/lib/marketflow`, существующего Caddy и сервисов на 80/443/3000. При конфликте установщик остановится, сохранив прежние приложения.

Установщик добавляет зависимости Ubuntu, отдельный Node.js 24.22.2 с проверкой SHA-256, пользователя `marketflow`, systemd-сервис и Caddy. Он не меняет SSH, firewall и настройки провайдера. Не включайте парольный SSH-вход специально: если сервер уже настроен для ключей, используйте ключ.

## 2. Добавьте секреты в GitHub

Откройте репозиторий → **Settings → Secrets and variables → Actions → New repository secret**. Секреты вводятся только в защищённых полях GitHub; не отправляйте их в чат, issues или файлы репозитория.

| Название | Значение |
| --- | --- |
| `SERVER_HOST` | Публичный IP или hostname SSH-сервера, без `http://` и пути. |
| `SERVER_PASSWORD` | Пароль пользователя `root` на сервере, если используется парольный SSH. Пароль панели управления может отличаться. |
| `SERVER_SSH_KEY` | Альтернатива `SERVER_PASSWORD`: отдельный закрытый SSH-ключ без passphrase; его публичная часть должна быть разрешена в `/root/.ssh/authorized_keys`. Задайте только один из этих двух секретов. |
| `SERVER_KNOWN_HOSTS` | Доверенная строка публичного ключа SSH-сервера, соответствующая адресу и порту. Как получить — ниже. |
| `CABINET_PASSWORD` | Новый пароль для входа в «Поток»: одна строка, 12–1024 символа. Используйте отдельный пароль, не пароль сервера. |

Итого нужны четыре секрета: адрес, один способ SSH-входа, ключ сервера и пароль кабинета. Для нестандартного SSH-порта добавьте **Variables → New repository variable → `SERVER_PORT`**. По умолчанию используется 22.

### Доверенный ключ сервера

В консоли сервера, открытой через вашего провайдера или уже проверенное SSH-соединение, выполните:

```sh
awk '{print "SERVER_IP", $1, $2}' /etc/ssh/ssh_host_ed25519_key.pub
```

Замените `SERVER_IP` в выводе адресом из `SERVER_HOST`. Полная строка вида `SERVER_IP ssh-ed25519 AAAA…` — значение `SERVER_KNOWN_HOSTS`. Для порта, например 2222, начало строки должно быть `[SERVER_IP]:2222`. Это публичный ключ сервера, не закрытый SSH-ключ.

Проверка ключа обязательна. Workflow не принимает неизвестный ключ автоматически и не использует `StrictHostKeyChecking=no`. Если ключ изменился после переустановки сервера, сначала проверьте новый ключ через консоль провайдера, затем обновите секрет.

## 3. Запустите установку

1. Откройте **Actions → Install Marketflow on Ubuntu → Run workflow**.
2. Выберите ветку `main`.
3. `domain`: ваш домен без `https://` и пути.
4. `username`: желаемый логин кабинета, например `dmitry`.
5. `confirmation`: введите `INSTALL`.
6. Нажмите **Run workflow**. Это запускает установку на сервер, которую вы разрешаете этим действием.

Публикация кода и обычный push ничего на сервере не устанавливают. Workflow запускается вручную, работает только с `main`, не запускается для PR и не перезаписывает существующую установку. Предварительная проверка неполной конфигурации не подключается к серверу.

После сборки и тестов GitHub передаст пакет по SSH. Пароль кабинета передаётся через стандартный ввод SSH и установщика; он не включается в командную строку, архив и сводку запуска. Временный SSH-ключ на runner и установочный каталог сервера удаляются при завершении. Сервер хранит scrypt-хеш пароля и создаёт мастер-ключ API-хранилища локально.

## 4. Откройте готовый кабинет

Успешный запуск покажет ссылку `https://ваш-домен` в **Summary** и **Environments → production**. Workflow проверяет действительный HTTPS-сертификат, доступность формы входа и отказ API без сессии (401). Проверка не отправляет запросов маркетплейсам.

Откройте эту ссылку с телефона или компьютера. Логин — указанный в запуске, пароль — значение `CABINET_PASSWORD`. Устройства имеют независимые сессии и общую базу заказов.

Заказы и API-ключи из Sites автоматически не перенесены. Заказы можно выгрузить CSV и импортировать; для истории и этапов нужен отдельный перенос. API-ключи вводятся заново в HTTPS-форме приложения, а не в GitHub Secrets. Границы первой версии и обслуживание описаны в [README-RU.md](README-RU.md).

## Если запуск не завершился

- Ошибка `Не задан …`: добавьте отсутствующий секрет/поле и повторите запуск; соединение с сервером ещё не выполнялось.
- `Permission denied`: проверьте именно SSH-доступ `root`, пароль или разрешённый публичный ключ; не отключайте проверку ключа сервера.
- `Host key verification failed`: проверьте доверенный ключ и формат адреса/порта в `SERVER_KNOWN_HOSTS`.
- Тайм-аут SSH: проверьте доступ сервера из интернета и правила firewall у провайдера. Workflow не открывает сетевые порты самостоятельно.
- Установщик завершился, но HTTPS-проверка не прошла: установка могла уже состояться. Проверьте DNS, Caddy и 80/443 по основной инструкции. Не удаляйте базу и конфигурацию и не запускайте повторную установку поверх них.

Это workflow первой установки. Обновление уже работающего сервера с резервной копией и откатом в данный workflow не входит.
